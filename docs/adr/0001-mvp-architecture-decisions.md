# ADR-0001：德州扑克策略教学 MVP 的架构决策

状态：已接受

日期：2026-08-09

## 决策 1：使用 PokerKit 作为 MVP 的唯一牌局规则权威

### 背景

牌局状态、合法动作、边池和摊牌存在大量边界情况。MVP 需要先保证人工录入场景和行动重放正确。

### 选择

使用 PokerKit 负责牌局规则裁决，并在 `pokerkit_adapter` 内转换为本项目的领域模型。PokerKit 的类型不得越过适配层进入 API、数据库或前端。

### 替代方案

- 自行实现完整规则引擎：可控性高，但边界风险和验证成本高；
- 同时使用多个引擎裁决正式牌局：会引入冲突权威；
- 使用 RLCard 或 OpenSpiel：适合研究和实验，不作为 MVP 正式牌局裁决源。

### 后果

PokerKit 升级只需集中修改适配层，但必须重新通过金标牌谱回归测试。研究库可以用于验证，不加入生产规则链路。

### 结算约束

弃牌、摊牌比较、分池、奇数筹码和派奖均由 PokerKit 的自动化状态机裁决。适配层只把 `ChipsPushing` 的实际筹码增量转换为 `SettlementResult`；奇数筹码规则记录为“底池顺序中第一位有资格获胜者取得余数”。这样可以保留 PokerKit 的唯一权威，同时让 API 获得可审计的派奖结果。

## 决策 2：MVP 不实现任意局面的动态 Solver

### 背景

动态 Solver 需要下注树、抽象、资源隔离、长任务调度和结果版本管理，容易把产品的教学与规则基础拖入高复杂度。

### 选择

MVP 只提供确定性分析、精确枚举或受控模拟、带来源的人工策划场景库，以及明确标注的原理教学。Solver 接口保留版本字段，但没有数据时不生成精确频率。

### 替代方案

- 首版直接接入外部 Solver：数据授权、延迟、成本和可复现性不可控；
- 先做简化 CFR：容易被误解为真实 GTO，且仍需大量验证；
- 等基础数据和评测集稳定后建设独立 Rust Solver 服务。

### 后果

产品可以较早交付可靠的规则和教学价值，但部分场景只能返回数学证据和原理解释，必须在 UI 和 Agent 中展示不确定性。

## 决策 3：使用事件式行动历史

### 背景

用户需要逐步录入、撤销、重做、恢复任意分析点，并能复现历史分析。

### 选择

以不可变、有序的 `ActionEvent` 序列作为事实输入；当前状态由初始筹码、盲注和事件重放得到。`raise-to` 表示行动后的总下注额，与增加额严格区分。

### 替代方案

- 只存每条街的最终快照：难以校验中间非法动作和恢复时间线；
- 直接存 PokerKit 序列化对象：上游类型泄漏且升级脆弱；
- 只存自然语言牌谱：不可可靠解析和复现。

### 后果

重放必须是纯的、确定性的，并报告第一个非法事件。快照可以作为缓存，但不能替代事件事实。

## 决策 4：Agent 只能解释已生成的证据

### 背景

语言模型不应承担牌局裁决、数值计算、范围发明或策略数据认证。

### 选择

Agent 只能通过结构化工具读取标准化场景、合法动作、范围、`EvidenceBundle` 和策略匹配结果，并返回带 `evidenceId` 引用的 `TeachingResponse`。

### 替代方案

- 让 Agent 直接从自然语言推断数值：不可审计且易产生幻觉；
- 让 Agent 自由输出 GTO 频率：没有策略数据时会制造虚假精度；
- 把 Agent 当规则引擎：无法覆盖边界情况和确定性要求。

### 后果

回答质量依赖证据生成器和证据版本；未绑定证据的数字必须被拒绝或删除，原理教学必须标记为 `principle_only`。

## 决策 5：金额使用整数最小筹码单位

### 背景

底池、下注和筹码守恒是规则正确性的核心。浮点数会造成舍入和序列化不一致。

### 选择

所有金额在领域层使用整数最小筹码单位；展示层才转换为用户友好的单位。赔率和权益等比例值可以使用明确精度的 Decimal 或带误差说明的数值类型，但不能把金额转换为浮点后再裁决。

### 替代方案

- 使用浮点数：实现简单，但会破坏边界比较和守恒校验；
- 使用字符串金额：可序列化，但运算和校验容易分散；
- 使用货币库：对真钱产品有价值，但 MVP 不涉及钱包或货币结算。

### 后果

API 和数据库必须明确单位；测试必须覆盖最小加注、不足最小加注的全下和筹码守恒。

## 决策 6：视觉输入延期，并复用同一套 ScenarioSpec

### 背景

截图和视频识别会增加 OCR、牌面识别、隐私、置信度和纠错问题，不应与基础规则正确性同时成为 MVP 的关键路径。

### 选择

MVP 只支持人工录入。未来视觉模块只能输出带置信度和待确认字段的 `ScenarioSpec`，不得建立第二套分析系统。

### 替代方案

- 先做截图识别：能提升入口体验，但会放大错误牌面和行动的风险；
- 接入实时牌桌：超出产品范围并涉及自动行动风险；
- 两套分析链路并存：会造成结果不一致和维护成本。

### 后果

需要在 `source`、`confidence` 和纠错元数据中预留输入来源，但当前不引入视觉依赖或实时接入。

## 决策 7：首版采用三个逻辑组件，保持本地开发轻量

### 背景

完整生产部署需要 Web、API、数据库、缓存和后台任务，但本地开发不应强依赖复杂集群。

### 选择

逻辑上分为 Next.js Web、FastAPI 和领域/分析核心；PostgreSQL、Redis、Agent 和异步任务按需要接入。领域核心可在没有数据库和 Redis 的情况下单独测试。

### 替代方案

- 一开始拆成多个微服务：运维和契约成本过高；
- 全部塞进前端：规则与数据安全无法保证；
- 直接建立复杂集群：不利于快速验证 MVP。

### 后果

边界由模块和接口先定义，部署可以后续容器化；异步任务不能侵入领域层。
