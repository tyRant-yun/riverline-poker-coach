# ADR-0008：仓库采用 AGPL-3.0-or-later 并强制第三方 provenance

状态：已接受；取代 ADR-0004 与旧依赖文档中“主项目保持宽松许可/sidecar 自动隔离许可”的部分
日期：2026-08-12

## 上下文

Riverline 是网络交互产品，已有 MIT/BSD/Apache/LGPL 依赖、候选 Apache evaluator、无许可证设计参考和 AGPL solver 研究。历史文档曾因“非商用”而计划让主项目保持宽松许可，并把进程/HTTP sidecar 视为许可隔离路径；这不足以表达产品负责人已确认的新基线，也不能替代实际组合、分发和网络交互义务审查。

## 决策

仓库整体以 `AGPL-3.0-or-later` 发布，根目录保存标准 GNU Affero GPL v3 文本。非商业/无收益不构成 GPL/AGPL 豁免。`THIRD_PARTY_NOTICES.md` 记录当前与候选组件的用途、精确版本/来源、许可证、依赖关系、决策和 provenance 要求；发布时还必须产生完整传递依赖/SBOM、NOTICE 和对应源码/修改信息。AGPL solver 不直接嵌入主依赖；只可作为有明确源码/构建/修改/许可记录的可选研究 artifact producer，并且进程、容器或 HTTP 边界只被视为故障架构，不被宣称为自动法律安全港。无许可证仓库的代码/资产不得复制。

## 备选方案

- 维持未声明或宽松主许可：保留更多闭源选择，但与确定的开放网络产品方向和 AGPL 依赖研究不一致。
- 因非商用而忽略 copyleft：触发点判断错误，不能采用。
- 直接将 AGPL solver 加入主依赖：许可兼容但显著扩大构建、维护、攻击面和实时故障风险，且产品并不需要同步 solver。
- 仅靠 sidecar 断言独立作品：架构简单，但组合判断取决于真实通信/集成，不能在 ADR 中作法律保证。

## 后果

- 向网络用户提供服务或分发时，必须实现并验证相应源代码访问、许可证/NOTICE 和修改说明流程；发布前仍需专业法律审查。
- 宽松许可证组件通常可在保留其通知的前提下进入 AGPL 项目；LGPL/其他条款仍单独履行，不能被仓库许可证覆盖掉。
- 策略表、模型和 solver/evaluator artifact 与代码一样需要来源、版本、配置、许可和 fingerprint；“公开可下载”不等于可复用。
- 旧文档保留历史技术上下文，但与本 ADR 冲突的许可结论不再生效。
