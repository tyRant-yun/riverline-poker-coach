# Riverline Token 管理与人机协作指南

状态：2026-08-13 初版

配套文档：[Riverline 重构执行复盘与后续协作规范](riverline-execution-retrospective.md)

## 1. 使用说明

本文用于指导 Riverline 后续开发中的 Token 预算、模型选择、任务拆分、上下文加载、审查和人与 Agent 的职责划分。

本轮没有可核验的逐任务 Token 账单，因此本文不声称给出项目的精确历史消耗。下文数字是经验区间，用于比较数量级和制定软预算，不作为平台计费记录。

## 2. Token 主要消耗来源

| 行为 | 经验消耗区间 | 说明 |
|---|---:|---|
| 新 Agent 加载完整历史 | 30k–100k+ 输入 | 历史对话、规划和仓库信息越多，固定启动成本越高 |
| 最小任务上下文启动 | 3k–12k 输入 | AGENTS、活动台账、直接 contract 和点名文件 |
| 全仓扫描或读取全部规划/ADR | 10k–50k | 通常不应成为任务默认动作 |
| 限定 diff 与直接契约审查 | 2k–10k | Reviewer 推荐模式 |
| 普通实现任务 | 15k–50k | 取决于范围、文件数量和返工次数 |
| Solver、恢复等复杂任务 | 40k–150k+ | 可以合理使用，但必须严格限制范围 |
| 一次结构化 handoff | 2k–8k | 能减少 Controller 的重复理解 |
| 一轮代码审查 | 8k–40k | 全仓审查昂贵，窄审查成本可控 |
| 无状态变化的轮询 | 每轮约 0.5k–3k | 单次不高，长期重复会明显累积 |
| 长测试日志进入上下文 | 2k–20k | 测试执行本身不是主要 Token 成本，读取输出才是 |
| 小修复创建全新任务 | 5k–20k 固定成本 | 经常超过代码修改本身 |

这些区间会随模型、仓库规模、上下文长度和任务复杂度变化。

## 3. 本轮主要低效消耗

按影响排序：

1. **新进程重复加载上下文。** 小任务也曾读取大量历史、规则和仓库信息。
2. **任务拆分过细。** 每个任务都要承担启动、worktree、handoff、验收和集成成本。
3. **用户体验问题发现过晚。** Bot、补码、随机发牌、摊牌、界面和洞察问题导致多轮返工。
4. **Reviewer 重建整个项目模型。** 很多审查只需要 `base..head`、直接契约和 focused tests。
5. **持续轮询。** 无状态变化的 `wait/read` 制造无效轮次。
6. **重复测试。** Worker、Reviewer、Controller 曾重复运行相同范围。
7. **高强度模型使用范围过宽。** 文档、CSS、台账或 fixture 不需要 Solver 级推理资源。

## 4. 值得投入 Token 的领域

下列消耗不应为了节约而过度压缩：

- 规则权威、金额结算和恢复一致性；
- 私牌权限与旧异步响应的失败反例；
- Range/Solver 的算法、采样、性能和 oracle 对照；
- 公共 DTO、事件和持久化 contract；
- 高风险改动的独立窄审查；
- 回归测试设计；
- 一次准确的结构化 handoff；
- 真实用户黄金旅程的失败诊断。

节约额度的目标是减少重复理解、无效协调和不必要审查，而不是减少必要推理。

## 5. 阶段 Token 软预算

| 用途 | 建议占比 | 默认模型与强度 |
|---|---:|---|
| Controller 规划、验收、台账 | 10–15% | Luna/Terra low |
| 普通实现 | 45–55% | Terra medium |
| 高风险算法或一致性实现 | 15–25% | Sol high，范围必须窄 |
| 独立窄审查 | 5–10% | 子 Agent；按风险选择 Terra/Sol |
| 集成、发布和意外修复储备 | 10–15% | 按风险升级 |

执行规则：

1. 意外修复储备低于 5% 时，停止新增非阻塞任务。
2. 同一问题连续两次修订仍失败时，停止堆叠 Token，重新检查 contract、任务边界或产品假设。
3. 不因为任务“重要”就自动选择最强模型，应依据推理难度和错误风险。
4. 小型 fixture、handoff 和台账修订优先使用原 Worker 与轻量模型。

## 6. 模型选择

### Luna/Terra low

- 文档和台账；
- handoff 修订；
- 简单 fixture；
- Git 事实核对；
- 低风险状态更新。

### Terra medium

- 普通前后端实现；
- API 接线；
- UI 和可访问性；
- focused tests；
- 普通集成修复。

### Terra high

- 跨模块状态流；
- 中等复杂度性能问题；
- 复杂但不涉及规则权威的诊断。

### Sol high

- Solver 和 Range 核心；
- 规则、金额和持久化；
- 恢复一致性；
- 私牌安全；
- 上述领域的独立窄审查。

## 7. 最小上下文包

新任务只应默认加载：

- Task ID 和单句目标；
- 精确 base commit；
- 允许和禁止修改的文件/模块；
- 直接依赖和公共 contract；
- 3–7 条验收标准；
- 必须保护的不变量；
- 允许运行的 focused tests；
- handoff 要求。

不要默认传递：

- 完整父对话；
- 所有历史 handoff；
- 完整 ledger；
- 全部 ADR/master plan；
- 与当前任务无关的产品设想；
- 全仓文件列表。

缺失的信息应按需补充，而不是在任务开始时一次性加载所有可能相关内容。

## 8. 上下文压缩后的恢复流程

1. 完整读取 `AGENTS.md`。
2. 读取 ledger 中活动任务、直接依赖和下一入口。
3. 读取当前任务 handoff。
4. 核对 Git branch、head 和工作树状态。
5. 使用增量 cursor 获取任务最新状态。

不得重新扫描全仓，也不得凭压缩摘要猜测提交、测试或交付事实。

## 9. 人与 Agent 的职责

### Product owner 负责产品真相

人最适合决定：

- 当前最痛的用户问题；
- 哪些功能必须保留或删除；
- 视觉和交互是否符合预期；
- 是否接受近似、降级或延后；
- 速度、精度、视觉和成本的优先级；
- MVP 与 SaaS 的阶段边界；
- 发布和外部写入授权。

UI、使用感受和产品价值不能只由自动测试判断。每个可体验批次由用户实际完成 2–5 手牌，通常比增加一次全仓审查更有价值。

### Controller 负责工程顺序

Controller 应负责：

- 将产品反馈转成纵向任务；
- 明确基线、依赖、文件边界和 contract owner；
- 最多并发两个独立实现任务；
- 消费 handoff，而不是重新阅读实现；
- 安全集成并维护中央 ledger；
- 只在需要产品选择时中断用户。

Controller 不应亲自长期开发、全仓审查或持续轮询。

### Worker 负责完整能力

一个 Worker 应尽量交付一条完整能力，例如：

- Advisor 从计算到 API 再到 Hero 区展示；
- Range 从公开事件更新到热力图和解释；
- Solver 从采样到 EV、置信区间和前端状态。

除非存在明确并行收益，不要把一条能力拆成 DTO、API、前端和 fixture 四个独立进程。

### Reviewer 负责真实风险

Reviewer 使用短生命周期子 Agent，不创建需要用户持续跟踪的长期任务。

默认只审查：

- 规则和金额；
- 私牌权限；
- 持久化和恢复；
- Solver/Range 算法与性能；
- 发布风险。

输入限定为：

- `base..head` diff；
- 直接契约；
- focused tests；
- 必须保护的不变量。

输出限定为 PASS/FAIL、P0/P1、最小反例和修复边界。

## 10. 推荐协作节奏

### 任务开始

用户提供：

- 当前最高优先级问题；
- 预期体验；
- 必须保留和允许删除的内容；
- 本轮速度、精度、视觉或成本偏好；
- 本轮额度限制。

Controller 回传：

- 最多两个实现任务；
- 每项交付和验收条件；
- 是否需要高风险审查；
- 大致成本档位；
- 明确不做的内容。

### 开发期间

- 不持续轮询。
- Worker 完成后由任务通知、用户呼叫或低频 heartbeat 唤醒 Controller。
- 没有风险变化时不发送重复进度。
- 小修复复用原 Worker。
- 两次修订仍失败时重新检查任务边界，而不是继续扩大实现。

### 批次完成

Agent 交付：

- 用户可体验的变化；
- 已验证证据；
- 未验证内容；
- 已知限制；
- 下一批建议。

用户只需体验核心旅程并反馈感受，不需要参与 Git、测试和 worktree 细节。

## 11. 用户指令模板

可以使用以下格式：

> 当前最高优先级：Range 难以理解。
> 目标：Hero 决策时能同时看到对手范围、变化原因和置信度。
> 必须：不读取真实对手私牌，更新延迟低于 50ms。
> 不做：暂不扩展 SaaS，不改复盘。
> 额度：中等，最多两个实现任务；高风险审查使用子 Agent。
> 完成后通知我体验，不持续轮询。

该格式明确产品结果、边界、风险和预算，技术拆解由 Controller 完成。

## 12. 任务启动检查

- [ ] 是否交付一个完整纵向能力？
- [ ] 是否有明确 base 和文件所有权？
- [ ] 是否共享 DTO/schema/事件 contract？
- [ ] 是否指定 contract owner？
- [ ] 是否只加载最小上下文？
- [ ] 是否选择了与风险匹配的模型？
- [ ] 是否只要求 focused tests？
- [ ] 是否真的需要独立审查？
- [ ] 是否保留了集成修复预算？
- [ ] 是否定义了真实用户体验门？

## 13. 核心原则

1. 用户用真实体验校正产品方向。
2. Agent 用 Git、handoff 和测试证据管理工程事实。
3. 先完成用户旅程，再增加基础设施。
4. 能复用原任务就不启动新任务。
5. 能读取 diff 就不读取全仓。
6. 能通过 handoff 验收就不重新理解实现。
7. 高强度推理只用于高风险问题。
8. 状态不变时不消耗新的推理轮次。
